# Backend: 3.8.0 to 4.0.0

> This document is provisional for the upcoming 4.0.0 release. It covers backend changes and operational considerations documented so far. Verify the procedure against the final release artifacts before upgrading production.

## General changes

### New authorization system

The new `authz` service manages principals, credentials, policies and permissions. Authorization can restrict actions on individual PKI entities and apply constraints to HTTP routes; services consult the engine to authorize requests and filter resources. Policies for WFX interfaces are also included. This replaces the previous gateway control based on token validation and the administrator role. The required configuration is described in the authorization migration section below.

### New jobs and workflows system

Siemens **WFX (Workflow Executor)** is integrated as a service for managing workflows and jobs, using its own PostgreSQL `wfx` database. The backend exposes a northbound interface (NBI) to manage workflows and jobs and a southbound interface (SBI) for devices, under `/api/wfx/nbi/` and `/api/wfx/sbi/`. Access can be protected by `authz` HTTP policies, including device identity constraints. In the monolithic development environment, WFX runs as a separate service and can be disabled with `-disable-wfx`.

### Notable fixes

- **CA import:** the imported certificate's authority key identifier (AKI) is preserved, and duplicate CA IDs are rejected before importing the key.
- **KMS key identity:** a key is identified by its ID and engine together, preventing keys with the same ID in different engines from being confused.
- **PKCS#11:** engine initialization is fixed, and context propagation through cryptographic operations is improved.
- **Alert and webhook security:** notification channels verify the server's TLS certificate and JavaScript filter execution is bounded. The Vault KV2 client also honors the CA configured through `ca_cert_file`.
- **DMS:** updating a DMS uses the ID in the URL and validates the request body, avoiding targeting an ID supplied in the body.
- **AWS IoT:** signed MQTT over WebSocket connection URLs are no longer printed in logs.

### Internal and functional changes

- **Device events:** dedicated event storage, endpoints to query and create events, and SSE streaming have been added. Historical events are migrated from the device record.
- **Storage:** PKI services use separate schemas in the PostgreSQL `pki` database; SQLite storage has been removed. `authz` and WFX use their own databases.
- **Cryptographic engines:** Azure Key Vault support has been added, and public-key resolution during CA import has been improved.
- **Containers:** service images have been updated to a distroless base and use a numeric non-root identity by default.
- **Go SDK and module:** the module now uses the `github.com/lamassuiot/lamassuiot/v4` path. Go consumers should review imports and adapt to changed interfaces.

## Migration

### Before upgrading

- Take a verifiable backup of PostgreSQL and of keys and CRLs stored on local volumes. Plan downtime for data migrations and prevent writes while data is copied.
- Identify legacy CA keys not yet registered in KMS, the cryptographic engines in use and existing VA roles.
- Prepare authorization configuration, connectivity to the OIDC provider and, where applicable, the switch to AMQPS.
- Identify persistent storage for KMS keys and VA CRLs, and ensure its data and permissions will be available to the upgraded services.

### PostgreSQL, certificates and keys

The 4.0.0 backend connects to the PostgreSQL `pki` database and uses the `kms`, `ca`, `va`, `devicemanager`, `dmsmanager` and `alerts` schemas. The `authz` and `wfx` databases serve separate purposes. Installations on 3.8.0 with separate per-service databases need to move their data and migration history to the corresponding `pki` schemas, preserving structure, indexes, constraints and data. The current `goose-lamassu` code applies migrations to an existing schema; it does not implement a command to move data between databases. Validate the transfer procedure against the final artifacts before upgrading.

To register missing legacy CA keys in KMS, use `ca-to-kms-migration`. The tool is idempotent and supports `--dry-run`; consult its [documentation](../../backend/cmd/ca-to-kms-migration/README.md) and adapt its configuration to the deployment.

The CA migration calculates `key_id` from the certificate's public key for records with an engine. If a certificate cannot be read, the migration skips it and logs a warning; review the migration logs and resolve affected records.

For manual migration, the current binary requires `search_path=<schema>`. Run the migrations against the `pki` database (`dbname=pki`); the binary does not validate the database name, so verify it before running the command:

```bash
./goose-lamassu "host=$DB_HOST port=5432 user=$DB_USER dbname=pki search_path=kms" up
```

Use the connection and TLS options appropriate for your environment. The existing binary documentation that specifies `dbname=ca`, `dbname=kms`, etc. does not match the current code.

### Authorization and authentication

4.0.0 introduces the `authz` service, which validates tokens and applies fine-grained authorization to service requests. Configure its JWKS endpoint, credentials for accessing `pki` and `authz`, policies and an initial principal able to administer the PKI. Check that the bootstrap rule matches the claims and roles issued by the OIDC provider: without a matching principal there is no implicit initial administrator.

Validation no longer uses the gateway's former JWT policy. Review the previous authentication and authorization configuration, and verify client and integration permissions after migration.

### AMQP

If TLS is enabled for AMQP, ensure clients connect to the broker's TLS port, commonly `5671`, and trust its certificate. Verify the effective configuration before upgrading, especially if plaintext AMQP was previously used.

Device-event SSE streaming creates a durable AMQP queue per process instance. Configure an appropriate expiration or cleanup policy on the broker to avoid accumulating queues from departed instances.

### Local storage and permissions

If KMS uses a filesystem engine or VA stores CRLs locally, consider preserving and, where necessary, transferring that data during the upgrade. Ensure the identity running the services can access keys, CRLs and cryptographic devices. Verify their operation before retiring the original data.

### API and device data changes

- **DMS reenrollment:** `reenrollment_settings.additional_validation_cas` is removed. The migration moves its contents to `reenrollment_settings.est_rfc7030_settings.client_certificate_settings.validation_cas`, replacing that field's previous value to preserve the trust set actually used. Update integrations that send or read the old field.
- **DMS update:** `PUT /v1/dms/:id` takes the ID from the URL and validates the update body. Adapt clients that relied on the ID in the body.
- **Device events:** historical events move from `devices.events` to the `device_events` table; the `events` field no longer appears in the device representation. Adapt consumers that read it and use the event endpoints. The migration transforms existing data.
- **Webhooks and notifications:** review HTTP configuration and trusted certificates. Alert webhook and Microsoft Teams channels verify the server's HTTPS certificate; configurations that relied on skipping verification may stop working. DMS webhook HTTP configuration has a data migration.
- **SQLite:** the SQLite storage engine has been removed. Deployments that used it must move to PostgreSQL and prepare their data transfer before upgrading.

### Post-upgrade checks

Check migration status, each service's logs, administrator and authorized client access, the AMQP connection, key availability, and CRL issuance and retrieval. Keep backups and old volumes until the upgraded backend's data and operation have been verified.
